- **Phase 2 — Vault (dispossession).** `packages/core`: `keys/secret-cipher.ts`+`local-secret-cipher.ts` (XChaCha20-Poly1305, ADR 0004), `token/scoped-token.ts` (compact Ed25519 envelope, not JWT — ADR 0003). `packages/connectors`: `Connector.call()`, three adapters (stripe real/mock-slack/mock-database). `services/vault`: `tool_credentials` table, `POST /credentials`, `POST /tokens` (independent VC verify + 60s token), `POST /call` (hot path, no I/O until token+revocation checked). `apps/cli`: `use`.

E2e proves 3-tool cutoff <1s.

## Gotchas for a new session

- **Image stack (Phase 7).** It shares the `pnpm dev` Postgres and seal store with `pnpm demo`, and they use the same ports, so run one at a time (`pnpm images:down` first). Its audit seed differs from the demo's, so switching is an audit key rotation: the first `custos audit-log` asks for `--accept-key`, and a fresh tools container asks once per key already in the log (ADR 0017). On Windows, pnpm's `bash` is WSL's `C:\Windows\System32\bash.exe`; the scripts work because Docker Desktop's WSL integration is on. `no-secrets-in-layers` takes ~5 min locally and lists PEM keys inside Debian ELF binaries (`libgnutls`, `gpgv` test vectors) as INFO by design.
- **The two Envoy mTLS test files flaked again 2026-10-30** (file-level FAIL in a full `turbo run test --force` while the image checks loaded Docker; 9/9 files, 128 tests pass when the package is run alone).
- **Features beyond the Notion plan must be logged** on Notion hub page "13 — Additional features (beyond the original plan)" (plain language + pitch line + status) — the user pitches from it. Update an entry's status when it ships.
- Native Windows Postgres already owns port 5432 — Compose Postgres is on **5433** (`infra/docker/docker-compose.yml`, `.env.example`, `drizzle.config.ts`). Don't "fix" this back to 5432.
- On Windows, WinNAT/Hyper-V periodically grabs a dynamic port range covering 5433 (seen as `5433-5532`), and Compose then fails with `bind: An attempt was made to access a socket in a way forbidden by its access permissions` — note that this is **not** "port already in use"; nothing is listening. Fixed once, persistently, by reserving the single port from an elevated shell: `net stop winnat` → `netsh int ipv4 add excludedportrange protocol=tcp startport=5433 numberofports=1 store=persistent` → `net start winnat`. The narrow `5433-5433` exclusion that this leaves behind is the fix, not the problem: it only removes the port from the ephemeral pool, and an explicit bind still succeeds. Restarting WinNAT briefly disrupts Docker networking for every running container.
- `pnpm test` requires the Compose Postgres up (`pnpm dev`); it migrates its own throwaway database, so `pnpm migrate` is only for the dev stack; the `.husky/pre-push` gate runs lint + typecheck + test, so a push fails on a stopped Docker daemon. `test:e2e` is deliberately not in that gate — slowest layer; run it by hand for cross-service changes.
- WinNAT can also reserve ranges that cover test ports. On 2026-10-02 it reserved **4105–4204**, and `apps/cli/src/verify.test.ts` (port 4201) failed with `listen EACCES` (3 tests time out at 30 s). CI is unaffected. Check with `netsh int ipv4 show excludedportrange protocol=tcp`. Releasing it takes the elevated `net stop winnat` / `net start winnat` described above, which briefly disrupts Docker networking. Done 2026-10-02, after which the full pre-push gate passed.
- **Root cause found 2026-10-28: this machine's TCP dynamic port range was 1024–15000**, not the Windows default 49152–65535 (`netsh int ipv4 show dynamicport tcp`). Any program's random port could land on a fixed test port (VS Code held 4510, failing vault's `server.test.ts` with `EADDRINUSE`) or on one of `fetch`'s blocked ports (sdk `client.test.ts` "bad port"), and WinNAT's reservations below fell inside test ranges. The founder reset it from an elevated shell: `netsh int ipv4 set dynamicport tcp start=49152 num=16384`, then restarted VS Code. If the low range comes back, check what changed it. Also: when one test task fails, Turborepo kills the others and Vitest leaves `vitest-coverage-*.lock` files in `%TEMP%`; a reused PID then makes the next run fail with "coverage report directory ... already in use". Delete locks whose PID is not a running `node` process.
- **Windows keeps reserving test ports after Docker Desktop restarts** (WinNAT): 4400–4999 on 2026-10-08, 4493–4592 and then 5659–5858 on 2026-10-18 to 2026-10-21, 4020–4219 on 2026-10-25 (vault `issue.test.ts`, ports 4211–4219). Symptom: `listen EACCES` in `services/vault` `server.test.ts` or `sdk` `mtls.e2e.test.ts`. Check `netsh int ipv4 show excludedportrange protocol=tcp`; the fix is the elevated `net stop winnat` / `net start winnat` below. First instance: Fixed-port tests in that range fail with `listen EACCES` until WinNAT is restarted from an elevated shell (`net stop winnat`, `net start winnat`). Keycloak tests use 8181; SSO route tests use none.
- **mTLS dev ports:** Envoy 5003 (→ revocation) and 5004 (→ audit); service TLS listeners 4013 and 4014 (41xx was once taken by WinNAT). Certificates are valid from one hour before generation (clock skew between Docker and host). The mTLS e2e uses Envoy container `custos-envoy-e2e` on 5701–5708.
- **mTLS certs:** never hand-edit permissions. `gen-certs.sh` runs as root, then gives files to the caller on Linux (Envoy runs as that user) or `envoy.key` to uid 101 on Docker Desktop (Envoy's own user); keys stay 0600. `.gitattributes` keeps `*.sh` LF, since `core.autocrlf` would otherwise break the script inside Linux containers. The proxy test's Envoy container is always named `custos-envoy-test` and removed before each run, so a killed run can't leave ports 5103/5104 taken (it did once, as `custos-envoy-test-<pid>`). `host.docker.internal` may resolve to IPv6, hence `dns_lookup_family: V4_PREFERRED` and the test upstreams listening on `::`.

- pnpm installed via `npm install -g pnpm@9.15.0` (`corepack enable` hit `EPERM` in this environment).

Tests don't need it — they pass `issuerKey` directly.

To check: point `DATABASE_URL` at a dead port and run `npx turbo run test --force --filter=<pkg>` — it must **fail**; if it passes, the var isn't reaching the task.
